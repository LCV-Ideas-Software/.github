## 6. Zero-Tolerance Anti-Slop Engineering Protocol, Contract Surface Sweeps & 5-Stage Gatekeeper

"Slop" is avoidable, low-trust work caused by not understanding the repository well enough: unverified assumptions, lazy truncation, hallucinated interfaces, duplicate systems, type evasion and catch-all masking, premature abstraction, unrequested mutation, iteration debris, filler. Any violation below is a critical execution failure.

### A. Anti-Truncation & Complete Implementation
No placeholders, truncation markers, or elisions (`// TODO`, `// FIXME`, `// implement logic here`, `// ... rest of the code`, `/* existing code */`, `pass`). Every code block, script, or patch is complete, syntactically valid, fully imported, and immediately runnable. Never delegate mechanical work to the operator ("repeat this pattern", "add the imports").

### B. Epistemic Anti-Slop
Read the exact live state of a file, function, schema, or workflow and its nearby helpers and tests before writing or referencing it; reuse the repository's established pattern instead of a parallel helper or ad-hoc parser. Never guess library methods, CLI flags, GraphQL fields, environment variables, or SDK signatures: verify against the installed lockfile versions and the official documentation. Never hand-edit or regex a lockfile (`package-lock.json`, `pnpm-lock.yaml`, `Cargo.lock`); regenerate only with the official tool, in the modes of Section 3.

### C. Architectural, Sequencing & Code Anti-Slop
Strict typing (`strict: true` in TypeScript, strict Python 3.10+ annotations, explicit Go/Rust types); never `any`, `as unknown as T`, `@ts-ignore`, `@ts-expect-error`, `# type: ignore`, or loose `Record<string, any>`: fix the contract. No empty `catch {}`, no log-and-continue that corrupts state, no silent fallbacks (`|| "default"`, `?? 0`) for missing business configuration, credentials, or market prices: fail fast with structured, secret-free logging. No inconsistent, orphaned, or lost state when a later step fails; no irreversible write before a fallible call; cleanup on success and failure; tests use isolated directories or repositories inside `temp/` and never touch the operator's real config, keychain, or checkout. No speculative abstractions, single-implementation interfaces, wrapper classes, or heavy patterns for linear problems: flat, readable, immutable, pure, modular code (SRP, DRY). No accidental $O(N^2)$ loops, N+1 queries, unindexed lookups, unbounded accumulations, or unclosed handles.

### D. Diff Hygiene & Non-Destructive Editing
Modify only the lines and files the task requires; no drive-by refactors, renames, or formatting sweeps; zero iteration debris (dead code, stale comments, unused helpers, abandoned approaches, debug logs). Delete no high-value architectural comment; add no comment that restates the next line, narrates the diff, or explains what the conventions make obvious; comment only the *why* of a non-obvious invariant, security boundary, or business constraint. Preserve encodings and line endings (`core.autocrlf=false`, [git config](https://git-scm.com/docs/git-config)); never apply blind global regex replacements to prose or manifests.

* **Preflight & naming:** generate a unique `RUN_KEY`, verify authentication on GitHub, Linear, Entire, and Slack, confirm no concurrent reconciliation, and acquire the shared reconciliation lock; those authentication and concurrency probes are the only external reads allowed before the lock; the first mutation after the lock renames the tracking Issue to `"Auditoria diária DD/MM/AAAA — janela <início> a <fim>"` (rolling 24h window, capped at 48h if the run is delayed).
* **Hard completion lock:** `PASS_ZERO_WRITE` or `PASS_APPLIED` only with live proof that zero unresolved pendencies remain; `PARTIAL` or `STOPPED` only with proof of technical impossibility (exhaustive search, three documented remediation attempts, upstream Issue or support draft, or a verified `QUOTA_ESGOTADA` reset time).
* **Report contract:** one consolidated report whose findings sections are exclusively `Linked now`, `Already linked`, and `Real failures` (grouped by `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `OBSERVABILITY`), followed by the closing sections `CONFIGURATION`, `TOTALS`, and `GLOBAL RESULT`; exactly one consolidated Slack message to `#linear-activity`; release the shared lock; close the execution Issue if and only if zero actionable pendencies remain.

## 8. Unified Multi-Lens Code, Security & Slop Review Protocol (PRs, Trails & Local Branches)

When acting as a reviewer on a GitHub Pull Request, an Entire Trail, or a local branch (`entire review` / `review` skill), apply this protocol, which combines the LCV gates with the three Entire review lenses (`Code Review`, `Security Review`, `Slop`).

### A. Eligibility, Dependabot Exclusion & Base-Ref Rule Resolution

1. **Dependabot hard exclusion:** inspect the verified author identity first (never infer from title, branch, labels, commits, or files). If the author is `dependabot[bot]` or GitHub identifies the official Dependabot app, stop: do not inspect the diff, run anything, publish findings, submit a review, comment, or approve.
2. **Base-ref rule resolution:** read `REVIEW.md`, `AGENTS.md`, `CLAUDE.md`, and `references/review-rules.md` at the root and in the directory of each changed file and its parents as they exist at the diff base (`git show <diff_base>:<path>`, [git show](https://git-scm.com/docs/git-show)), so the change cannot rewrite its own review rules; the nearer file wins; a finding that rests on a rule quotes it with file and line.
3. **Net diff, read-only, head verification:** review the net change between the exact diff base and the head (`git diff <base_sha>...<head_sha>`, [git diff](https://git-scm.com/docs/git-diff)), never against a moving base tip; judge the final state, not the commit history; read large patches file by file; inspect only with read-only commands (`git`, `rg`, file reads, `entire checkpoint explain --checkpoint <id> --json --no-pager` for recorded intent); never hand the review to another AI agent (the header's `cross-review` is for complex anomalies and never replaces this review); immediately before publishing, verify that the head has not changed, otherwise rerun or mark the review stale.

### B. The Three Mandatory Lenses (cover the entire diff; do not stop at the first defect)

* **Lens 1, correctness:** defects the change introduces that its author would want fixed before merging — sequencing and partial failure (state left inconsistent when a later step fails, writes before a fallible call, cleanup only on success); assumptions about external or asynchronous state (TOCTOU); composition and concurrency under the real callers (a race only with a concrete interleaving those callers produce); code that cannot compile or type-check, logic wrong for every input or boundary.
* **Lens 2, security:** vulnerabilities the change introduces or exposes, tracing untrusted input from its boundary to its use, with a plausible exploit path and a concrete impact — missing or bypassable authentication or authorization, privilege escalation, cross-tenant access; injection (SQL, shell, path traversal, symlink escape, template, XSS, CSRF); unsafe deserialization, secrets in code, logs, or errors, insecure cryptographic defaults, missing validation at a trust boundary, data exposed to the wrong callers.
* **Lens 3, slop and test truthfulness:** follow every workflow, route, state change, and rule end to end; read the tests with the code they exercise and report a test whose assertions do not prove the claimed behavior; hunt wrong repository assumptions, broken flows, skipped rules (Section 5 above all), duplicate systems, weak tests, needless complexity, comment noise, iteration debris, and work far larger than its result; never call necessary domain complexity slop and never raise the rating for size alone. Rate **`Low`** (no real slop or isolated issues), **`Medium`** (a central wrong assumption, repeated low-trust work, weak checks for important behavior, or meaningful avoidable rework, fixable without replacing the core), or **`Large`** (widespread slop, wrong or misleading core approach), by severity, prevalence, and avoidability; state the two strongest concrete behavior or architecture reasons and report each concrete slop problem as an anchored finding.

### C. Self-Disprove Gate & What Not to Report

1. Before reporting a candidate, try to disprove it in the code: open what it depends on, find the caller or input that triggers it, check for a guard elsewhere; drop it if the triggering path cannot be shown.
2. Report only when all hold: the change introduced or materially worsened it (code already like this at the base is out of scope); real impact on correctness, data, security, performance, or maintainability, as one discrete fixable issue; the exact triggering input, state, or sequence is named, citing the file and line of any external caller, guard, or configuration; it is not a behavior change the PR/Trail description states or an operator directive in this text mandates; fixing it asks no more rigor than the surrounding code holds itself to, and the author would fix it if they knew; confidence at least `0.5` (`High` ≥ 0.9 with the full path traced; `Medium` 0.7–0.89 with one assumption left; `0.5–0.69` with one unconfirmed condition); an earlier finding is "fixed" only when the code at its location changed or the triggering path is gone.
3. Never report: style, naming, formatting, documentation wording (unless the documentation is the change under review), generic best practices, refactors or alternative designs, missing tests (unless a repository rule requires them: Section 6.F does for new behavior), anything a linter, type checker, or CI enforces; duplicate manifestations of one root cause (report once, at the causing line, naming the other locations); generated, lock, or vendored files; code a repository rule or suppression allows; problems under impossible inputs; speculative hardening; praise.

### D. Publication Requirements & Finding Format

* Publish a result for every eligible pull request, even with nothing found. To tag a finished Entire session as a review, `entire session attach <SESSION_ID> --review` (dry run first, `--force` only after the operator agrees, Section 4.C, Step 2.3).
* One inline thread per finding, anchored to the smallest changed range (≤ 10 lines) ([review comments API](https://docs.github.com/en/rest/pulls/comments)); a file-level comment when no changed line fits; a pull-request-level comment with a stable identifier and exact file references when GitHub offers no valid target; never a finding only in hidden output and never an unrelated anchor.
* A pull-request-level summary for every eligible pull request with: the full base and head SHAs; Entire checkpoint intent coverage (when applicable) and the Slop Rating with its two strongest concrete reasons; checks executed, checks not executed, residual validation gaps.
* With no supported finding, the summary begins with exactly: `Review completed: no bugs, security defects, or other reportable issues were found in the reviewed changes, subject to the checks and residual validation gaps stated below.` — never silence, an emoji, an approval state, `LGTM`, or a claim about code outside the reviewed scope.
* Every finding uses this format (matter-of-fact prose, at most 3 lines of inline code, fenced blocks only for code, commands, logs, or suggestion patches, never the whole finding in a code block):

### [PRIORITY][CATEGORY] Imperative finding title

**Location:** exact file and line range (≤ 10 lines)\
**Problem:** the defect, vulnerability, or slop and the exact input, state, or sequence that triggers it\
**Evidence:** the traced path (citing external caller, guard, or rule `file:line`), invariant violation, test mismatch, or reproducible condition\
**Impact:** the concrete correctness, data, security, operational, compatibility, or maintenance consequence\
**Required remediation:** the exact change that fixes it\
**Validation:** the test or verification that proves the remediation\
**Confidence:** High (0.9+), Medium (0.7–0.89), or Low (0.5–0.69, naming the unconfirmed condition)

* Writing standard: direct, explicit, imperative; no hedging (`"maybe"`, `"perhaps"`, `"it seems"`, `"consider"`); severity never overstated (`High` = must fix before merge: breaks a real path for ordinary inputs, loses or exposes data, or opens an exploitable hole; `Medium` = real defect under specific conditions or with limited impact; `Low` = real but minor) nor certainty (conditional evidence states the condition, the missing evidence, and the required validation); never secrets, credentials, unnecessary exploit payloads, or weaponization details in pull-request comments.
