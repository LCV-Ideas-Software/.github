## 8. Pull Request Review Rigor, Publication & Finding Format

### Review Rigor

* Review the exact changes between the pull request base commit and the current pull request head commit, together with only the surrounding repository context needed to validate those changes.
* Record the full base commit SHA and the full head commit SHA in the published review summary.
* Immediately before publishing, verify that the pull request head SHA has not changed. If it has changed, do not present the review as current; rerun the review against the new head SHA or explicitly mark the existing review as stale.
* Evaluate, where applicable: functional correctness, security, authentication, authorization, access-control boundaries, input validation, injection risks, secret handling, cryptography, privacy, data integrity, transactions, concurrency, race conditions, resource exhaustion, performance, error handling, backward compatibility, migrations, dependency risk, observability, tests, and maintainability (while strictly respecting the operator's product and repository exceptions in Section 4).
* Report only issues introduced or materially worsened by the reviewed changes and supported by concrete evidence.
* Do not report style-only nits, generic best-practice reminders, duplicate manifestations of the same root cause, or speculative concerns without an actionable validation path.

### Publication Requirements

* Always publish a review result for every eligible pull request, even when nothing is found. (Dependabot pull requests are excluded and must not be reviewed or reported as reviewed).
* For every eligible pull request, publish every supported finding that meets the active reporting threshold directly on the GitHub pull request.
* Create one separate inline review thread per finding, anchored to the smallest relevant changed-line range.
* Do not leave a reportable finding only in internal, private, hidden, or suppressed output.
* If a finding cannot be anchored to a valid changed line, create a file-level review comment when supported.
* If GitHub provides no valid line-level or file-level target, publish a separate pull-request-level comment containing a stable finding identifier, exact file references, and the reason an inline thread was not possible.
* Never attach a finding to an unrelated line merely to force an inline thread.
* Publish a pull-request-level review summary for every eligible pull request, including when no findings are found.
* Include the reviewed base SHA, reviewed head SHA, checks executed, checks not executed, and residual validation gaps in every review summary.
* When no supported finding is found, begin the pull-request-level review summary with the exact textual statement:
  `Review completed: no bugs, security defects, or other reportable issues were found in the reviewed changes, subject to the checks and residual validation gaps stated below.`
* The no-findings completion statement must be published as textual content in the pull-request-level review summary.
* Do not replace the no-findings completion statement with silence, an emoji reaction, an approval state, `LGTM`, a generic success message, or any other shorthand.
* Do not claim that no bugs exist. State only that no reportable issues were found within the reviewed changes, executed checks, available evidence, and explicitly stated validation limits.

### Finding Format

Use structured Markdown for every finding:

### [PRIORITY][CATEGORY] Imperative finding title

**Location:** Exact file and line range  
**Problem:** The defective behavior  
**Evidence:** The code path, invariant violation, test result, or reproducible condition  
**Impact:** The concrete correctness, security, operational, or compatibility consequence  
**Required remediation:** The exact change required  
**Validation:** The test or verification needed to prove the remediation  
**Confidence:** High or Medium

* Use the priority or severity vocabulary native to the active review mode.
* Use fenced code blocks only for code, commands, logs, or GitHub suggestion patches. Do not wrap the entire finding in a code block.

### Writing Standard

* Use direct, explicit, and imperative language.
* Do not use vague hedging such as "maybe", "perhaps", or "consider".
* Do not overstate certainty. When evidence is conditional or incomplete, state the exact condition, missing evidence, and required validation.
* Do not add praise, filler, obvious code summaries, or non-actionable commentary.
* Do not publish secrets, credentials, unnecessary exploit payloads, or weaponization details in pull-request comments.

## Entire and GitHub together (enterprise standard)

This section applies to agent sessions on a local workstation with the Entire
CLI installed. It does not apply to agents that run in GitHub Actions or in a
provider's cloud, such as the `@claude` workflow, Codex cloud tasks or the
Copilot coding agent: they commit through their own tools and follow their own
instructions.

Entire and GitHub run together, in parallel, at all times. GitHub remains the
source of truth and the home of the controls (signed commits, rulesets, CodeQL,
reviews); Entire captures a checkpoint when a commit is made and syncs it when
the commit is pushed. Work recorded in only one of them is incomplete.

1. Start the agent session at this repository's root, or at its worktree under
   `.worktrees/`. A session opened in a parent folder is not attributed to this
   repository.
2. Before working, run `entire status --detailed`. If the hooks are missing, run
   `entire configure --force`; do not reinstall what already works.
3. Keep the result in files of this repository. Work that changes no file here,
   such as API-only or console operations, produces no checkpoint.
4. Commit with a local, signed `git commit`; never through the GitHub API or web
   editor, and never with `--no-verify`, so that Entire's Git hooks run.
   `.entire/settings.json` sets `"commit_linking": "always"`, so commits link to
   the captured session without a prompt.
5. The hook writes the `Entire-Checkpoint` trailer when the commit is made. Never
   invent a checkpoint ID the tool did not create.
6. Push with `git push`, then prove that the checkpoint reached GitHub and Entire:
   `git ls-remote origin 'refs/entire/*'` lists the ID from the commit trailer,
   and `entire checkpoint explain <id> --repo gh/<owner>/<repo> --json` answers
   when run from a clone of another repository. Inside this repository's own
   clone the command reads the local copy and answers even when Entire never
   received the checkpoint.
7. Merge with squash. A squash merge makes a new commit on `main` without the
   branch commits' trailers, and the dispatch reads only `main`: end the squash
   commit message with the `Entire-Checkpoint` lines the hook wrote on the pull
   request's commits, copied as they are, one per checkpoint proven in step 6
   (operator decision of 2 November 2026).
8. Once per pull request, after it is merged, generate a remote dispatch:
   `entire dispatch --repos gh/<owner>/<repo> --since <author time of the PR's first commit> --voice neutral`.
   Take that time from `gh pr view <number> --json commits -q '.commits[0].authoredDate'`:
   checkpoints are created at commit time, before the PR exists. The window can
   also include other work merged in the same period. Add `--jurisdiction <slug>`
   when the repository is placed outside your home jurisdiction
   (`entire auth status` shows the home one).
   Every dispatch must have a title. The CLI has no title option, so take the
   newest setup for this repository from
   `entire api --jurisdiction <slug> /api/v1/me/dispatch-setups` and run
   `entire api --jurisdiction <slug> -X PATCH /api/v1/me/dispatch-setups/<setup-id> -f "name=<repo> — PR #<number>: <PR title>"`.
   Use the same jurisdiction slug that generated the dispatch in both commands:
   each jurisdiction lists only its own setups. In Git Bash on Windows, prefix
   `entire api` with `MSYS_NO_PATHCONV=1`, or the `/api/v1/...` path is rewritten
   into a Windows path.
   Post the dispatch title and markdown as a comment on the pull request, with
   the PR's checkpoint IDs read from its commit trailers; the dispatch must cover
   them. Entire allows one generation per minute per account: after a rate-limit
   answer, wait 60 seconds and retry once. Write `<owner>/<repo>` exactly as GitHub
   spells it: a different case answers that the repository was not found.
   "No checkpoints" for this window means the squash message lacks the trailer
   lines of step 7 or step 6 failed; never create an artificial commit to fill a
   dispatch.
9. Report configuration, executed-and-proven evidence, and pending items
   separately.
