## 2. Verdict

**Recommendation, confirmed by the analysis below: retire the reconstruction design, with a precise cut.** The causal chain rests on documentation facts and code structure:

- (a) the chosen Slack primitive (webhook trigger) is documented to answer only `{"ok": true}` with no execution/invocation ID [E-A8];
- (b) no documented API exists to query or cancel a specific execution from data passed into the trigger [E-A10 — absence verified];
- (c) to recover correlation, the system promoted `apps.activities.list` (an activity-log API restricted to workflow apps, retention undocumented [E-A9]) into the mechanism that reconstructs delivery truth;
- (d) that required a temporal checkpoint coupled to ownership, hydration and readiness — three checkpoint writers share a duplicated clamp SQL [E-C1] plus two more clamps monitor-side [E-C4];
- (e) the resulting machine carries a 10-state delivery enum [E-C3] and 6 auxiliary tables, and produced the records of §1.

**What is KEPT (not rewritten):** webhook ingress with HMAC verification, event allowlist, normalization, and dedup by GitHub delivery GUID (`INSERT ... ON CONFLICT(delivery_id) DO NOTHING` [E-C6]); the queue topology (alerts/activity + DLQs); D1 as the durable store; the "GitHub Slack Webhook Redelivery" workflow. GitHub's delivery GUID is documented as stable across redeliveries [E-A7], so redelivery + dedup is safe by construction.

**What is REPLACED entirely:** the egress path (Slack Workflow triggers, receipts, `/slack/progress`), the reconstruction monitor, and the entire checkpoint/hydration/scan/reconciliation machinery.

## 3. Defect inventory (properties of the code at SHA 2c329cd1, each evidence-linked)

- D1 frontier×hydration coupling: any pending hydration freezes the frontier (monitor: `reportCheckpointUs = hasPendingHydration ? previousCheckpointUs : evidenceCheckpointUs` [E-C4]).
- D2 duplicated clamp in the Store: checkpoint advance also blocked by any `slack_trace_hydration_registry` row whose status column holds `pending` [E-C1].
- D3 delivery clamp is separate and load-bearing: it protects the two ambiguous delivery rows and cannot be silently removed [E-C1].
- D4 global state can diverge from the locally-hydrated subset (budget of 2 trace hydrations per run vs. global pending count).
- D5 no safe automated recovery path exists for `accepted_by_trigger` (2xx received, no receipt/trace/ts — resend may duplicate, advancing may erase the correlation window).
- D6 the monitor acts as source of truth: it reconstructs and mutates ownership, delivery rows, checkpoint, debt, manual review and replay.
- D7 the delivery clamp is broader than its documentation: `OR slack_trace_id IS NULL` pins the checkpoint on ANY non-legacy row without an attached trace — including `delivered` rows confirmed via receipt and `manual_review`/`dead_letter` rows [E-C1].
- D8 ~700 lines of dead Store code: `recordSlackTrace`, `resolveSlackTraceIdentityBySendExecutionId`, `getSlackActivityCheckpoint`, `finalizeSlackReconciliationReport`, `advanceSlackActivityCheckpoint` sit on the interface and have no caller in `index.ts` [E-C7] — two parallel implementations of the same resolution semantics kept in sync by hand.
- D9 unreachable version bridges: the worker keeps v2–v4 parsers only to answer `409 reconciliation_upgrade_required`; the monitor carries full v2–v4 client paths although the checkpoint endpoint always answers `reconciliation_version: 5` [E-C7].
- D10 a byte-exact protocol seal on the hot path: D1 triggers freeze `relay_state` by byte identity; every queue message, cron and health check re-reads `sqlite_schema`; the seal validates only the FORMAT of `WORKER_VERSION.tag` (any 40-hex passes), not the deployed revision.
- D11 by design, the readiness probe and the monitor merge three distinct concerns — liveness, readiness and alerting — into single fail signals: the probe SQL [E-C2] maps ANY `manual_review`/`dead_letter` row, overdue receipt or hydration-debt row onto the unavailable response of the kind recorded in [E-E1], and the monitor's code path [E-C5] throws the exact error recorded in [E-E2] even when its own durable reconciliation ended without error. Consequence of the design: operational debt has no representation other than making the whole probe/scheduled job fail ("infinite red"), which the prior review round had already objected to.
- D12 self-referential alerting: the payload recorded for delivery `d43b2d70` [E-B] is itself an alert about the `slack-production` environment (event `deployment_status`) — the design routes alerts about the system's own troubles through that same system.
- D13 secret rotation left mid-state (`SLACK_RELAY_SIGNING_ACTIVE_SLOT: "next"` pinned in wrangler config and in the monitor job env; the GH secret named `SLACK_RELAY_SIGNING_SECRET` injected as env `..._NEXT`) and hardcoded identifiers (channel IDs, worker hostname, Slack function IDs) across worker, monitor and Slack app.
- D14 three time units on the critical path: ms (`updated_at`), µs (checkpoint; `updated_at * 1000` in the clamp SQL [E-C1]), unix-seconds strings (`relay_timestamp`).

## 6. New design

### 6.1 Data flow
GitHub webhook → ingress (HMAC, normalize, presence fence per §6.8, `INSERT dispatch_outbox state='queued'` keyed by GUID; the INSERT and — in F2 — the old-path insert commit in ONE `batch()`; queue publish follows the commit) → consumer: CAS claim `queued → sending`, recording `last_send_start_ms`, lease 90 s (0 rows changed ⇒ duplicate ⇒ ack) → `chat.postMessage` with `metadata.event_payload.delivery_id`, **hard client timeout 30 s (abort)** → outcome classified by §6.2's total classifier, applied in one `batch()` with an audit row. Plain top-level message only: the dispatcher never sets `thread_ts`/`reply_broadcast` (R15).

### 6.2 Total outcome classifier and state machine (single writer = the worker)
**Classification precedence: the HTTP status is classified first; `ok`-body rules apply ONLY to HTTP 200 responses.**
- HTTP 200, `ok:true`, `ts` → `delivered` (canonical proof).
- HTTP 200, `ok:false` with a code in the MANUAL list — `invalid_auth`, `token_revoked`, `account_inactive`, `missing_scope`, `channel_not_found`, `not_in_channel`, `is_archived`, `restricted_action`, `msg_too_long`, `no_text`, `invalid_blocks`, `invalid_metadata_format`, `invalid_metadata_schema`, `metadata_too_large`, `metadata_must_be_sent_from_app`, `message_limit_exceeded` → `manual` (deterministic config/payload failure; automatic retry cannot succeed; no automatic resend ⇒ no duplicate risk).
- HTTP 200, `ok:false` with `internal_error`, `fatal_error`, or ANY code not in the MANUAL list → `ambiguous` (the descriptions do not state whether effects were applied [E-A15] — fail-safe).
- HTTP 429 (regardless of body, including an `ok:false ratelimited` body) → `ambiguous`; the `Retry-After` value is recorded and honored by the resolver's scheduling [E-A12].
- Everything else — unexpected 3xx/4xx, 5xx, network timeout (including our own 30 s abort), TLS/DNS/socket failure, malformed or non-JSON body — → `ambiguous`.
- Worker crash after send: lease expiry makes the row resolver-input.
**There is NO automatic resend of any kind — the state `retry_scheduled` does not exist.** Further transitions: `ambiguous → delivered` (resolver FOUND); `ambiguous → manual` (resolver PROVEN-ABSENT, carrying its full evidence; or resolver budget exhausted, inconclusive); `manual → delivered` (operator marks with ts evidence, or a late canonical `ok:true` + `ts` from a previous attempt arrives — proof beats inference; audited); `manual → closed_manual` (audited closure without resend); `manual → queued` (the ONLY resend path: explicit operator action, marked possible-duplicate, arming §6.3.3 verification); queue-DLQ exhaustion → `dead_letter` (alarmed; operator menu). Ambiguity is first-class and never resolves silently.

### 6.3 Idempotency contract (invariant I1)
PK = GitHub delivery GUID end-to-end; transport at-least-once; effect deduplicated by CAS claim. **I1 — a resend may be initiated ONLY by the operator, via the audited menu, marked possible-duplicate. The resolver's verdicts are EVIDENCE presented to that decision, never triggers. The system never creates a possible duplicate by itself.** The complete duplicate surface is therefore exactly ONE case: an operator-accepted possible-duplicate — and even it is guarded: the operator resend arms the §6.3.3 verification scans, and any materialized duplicate is detected and repaired (§6.3.2), audited and alarmed. Server-side late materialization having NO documented latency bound [E-A16] is thereby rendered harmless: with no automatic resend there is nothing for a late post to race against except an explicit human decision that was made knowing the risk. **Late-proof rule:** if a consumer receives `ok:true` + `ts` after its `WHERE state='sending'` CAS no-ops, it MUST unconditionally append the ts to `dispatch_audit` and then attempt `CAS ambiguous → delivered(ts)` first and `CAS manual → delivered(ts)` as fallback — canonical proof always lands durably and wins over inference regardless of which state the resolver reached first (R2 amended). **Amended (Copilot suppressed finding F4/F2, review 4943164344):** the append and both CASes commit in ONE `batch()`, because an append committed in a SEPARATE operation could survive a worker termination that never reached the CAS, leaving the row `manual` with the proof only in the journal — and queue redelivery then ACKs an unclaimable manual row, so proof never beats inference without an operator. Consequence to state plainly: "unconditional" is unconditional with respect to the row's STATE (the append lands whichever CAS applies, or none), not with respect to a CONSTRAINT failure — a batch rejected by `UNIQUE(destination, slack_message_ts)` now rolls the append back with the transition, which is the §6.1 all-or-nothing rule applied to this path.

### 6.3.1 Resolver specification
- **Normalization first**: rows in `sending` with `lease_until_ms < now` are CASed to `ambiguous` (audited `lease_expired`) before any verdict; **all verdict CASes run WHERE state='ambiguous' only** — no verdict races a live consumer CAS.
- **Query**: `conversations.history(channel = destination channel, oldest = (created_ms/1000) − 300, inclusive = true, limit = probed page size, include_all_metadata = true)` [E-A14]; **no `latest` bound** (scan up to Slack-now; the cooling-off floor governs the upper edge); ms→seconds conversion at this boundary only.
- **Pagination exhaustion** := `response_metadata.next_cursor` empty AND `has_more` false; an absent `response_metadata` counts as an empty cursor; the contradictory state (empty cursor AND `has_more` true) is INCONCLUSIVE, never exhaustion; a partial scan is never absence.
- **Match**: `message.metadata.event_type == "github_relay_delivery"` and `metadata.event_payload.delivery_id == GUID` (top-level messages only — R15).
- **Verdicts** (each in one `batch()` with an audit row): **FOUND** → `→ delivered(ts, channel)`; **PROVEN-ABSENT** → `→ manual`, carrying its full evidence in the audit row (scan window, pages, exhaustion proof, floor timestamp, retention check) and raising the observer alarm — it never schedules a resend by itself; the verdict is permitted ONLY when ALL hold: `now ≥ last_send_start_ms + 30 000 (client timeout) + 90 000 (lease) + 60 000 (margin)` — the **cooling-off floor**. The floor guarantees no CLIENT-side attempt is still executing (our fetch aborts at 30 s; the lease has expired; the worker invocation is gone); Slack documents NO maximum latency for a request's effects to materialize [E-A16], so a server-side late post beyond the floor remains possible in principle — that residue is not assumed away but detected and repaired by §6.3.2. Further preconditions: pagination exhausted; workspace retention verified ≥ resolver horizon (R9); metadata round-trip proven in F2 (R14); **INCONCLUSIVE** otherwise (history 429/error/partial scan/floor not reached) → stay `ambiguous`, `resolver_attempts + 1`; after 6 attempts within 1 h → `manual`; audited per attempt.
- **Budget**: ≤ 2 rows per cron run × ≤ 3 pages per row. **F0 probe (house empirical practice)**: with the real bot token, probe the accepted `limit` and sustainable request rate on `conversations.history`, and prove the metadata round-trip (post + re-find via this exact match rule; `metadata_must_be_sent_from_app` must NOT fire for the bot token [E-A15] — if it does, the fallback correlation key is the GUID embedded in a fixed block element, and the match rule switches to it before F2). If the 2025 clampdown applies (1 req/min, 15 objects), the degraded budget makes exhaustion infeasible — a documented DECISION POINT before F2, not a silent degradation.
- **Persistence**: `dispatch_outbox.resolver_attempts`, `dispatch_outbox.last_send_start_ms`; every verdict and every inconclusive attempt appends to `dispatch_audit`.

### 6.3.2 Duplicate repair (closes the undocumented-latency residue)
Whenever the resolver's match rule returns MORE THAN ONE message carrying the same `metadata.event_payload.delivery_id` — the signature of a late server-side materialization after a legitimate resend — the EARLIEST `ts` is canonical: it is recorded on the row (`delivered`), and every later copy is deleted via `chat.delete` (documented; with a bot token the method "may delete only messages posted by that bot" [E-A16] — exactly our case, `chat:write` scope already held). Each deletion is audited (`dispatch_audit` row with both timestamps) and raises an alarm on `/status` (`repaired_duplicates` counter), so a nonzero rate is visible instead of silent. The FOUND verdict therefore subsumes repair: found-one ⇒ record; found-many ⇒ record earliest + delete rest + audit + alarm (RED R17).

### 6.3.3 Mandatory post-resend verification (closes the delivered-and-forgotten gap)
A row delivered via an OPERATOR resend (`manual → queued`, the only resend path) does NOT leave the resolver's attention: it carries `verify_scans_remaining = 2` and `verify_after_ms = delivered_at + 15 min`. Rows with `verify_scans_remaining > 0` and `verify_after_ms ≤ now` are resolver inputs EVEN IN state `delivered`. Each verification scan runs the §6.3.1 match rule over the full window (row `created_ms − 300 s` → now): exactly one match ⇒ decrement `verify_scans_remaining` and schedule the second scan at `delivered_at + 24 h`; more than one match ⇒ **repair from `delivered`** — the EARLIEST ts becomes canonical (`CAS delivered → delivered` updating the recorded ts if needed), every later copy is deleted via `chat.delete`, both actions audited, `repaired_duplicates` incremented (RED R18). A late materialization beyond the 24 h horizon is a documented accepted residual — with the explicit property that it is never unrepairable: ANY later scan that observes a multi-match (including an operator-triggered sweep from the menu) applies the same repair (RED R19). Verification scans share the resolver's budget and are INCONCLUSIVE-safe: a failed scan does not decrement the counter.

### 10.1 Residual risks

- **Residual 1 (ELIMINATED) — mode-off retries could dead-letter a healthy row.** The consumer previously answered a mode-off message with `retry({ delaySeconds: 60 })`. Every retry consumed the queue's finite retry budget, so a long mode-off window pushed the message to the DLQ; if the operator re-enabled the mode before that DLQ message was consumed, the DLQ handler's mode-off guard no longer applied and a perfectly healthy `queued` row was transitioned to `dead_letter` — recoverable only through the operator menu, which §6.8/R20 forbids ("each accumulated row re-enters the NORMAL pipeline"). Raised by codex in cross-review round 4 and FIXED rather than declared: in mode off the consumer now ACKS the message. The row stays `queued` and untouched (visible through the `queued_backlog_stale` alarm), no retry budget is consumed, no DLQ trip happens, and the cron's stale-queued republish — already gated on `mode !== "off"` — re-enters the row automatically on re-enable, with no operator step.
- **H8 — the dispatcher paces its own sends (§6.4 and §6.7 extended).** §4 item 4 records Slack's ~1 message/second/channel limit as a platform constraint, but §6 never gave the dispatcher a mechanism for it: §6.7 only sets `max_concurrency 1` per queue, which serializes consumers without spacing them. The legacy path did pace, through a durable reservation in `relay_state`. Without an equivalent, a burst of alerts produces 429s, every one of which is `ambiguous` by §6.2 and — since no automatic resend exists — ends in operator work. The dispatcher therefore reserves a send slot before each claim: migration 0010 gains `dispatch_rate_limit(destination PRIMARY KEY, next_send_ms)`, and the consumer takes the slot with a conditional upsert (`DO UPDATE ... WHERE next_send_ms <= now`) using the legacy interval verbatim (6.1 s). When the slot is held the queue message is RETRIED with the remaining wait — never acked, never sent, and never in mode off, where the R20 ack path wins. Shadow rows are exempt: they perform no egress (§9.A1). The reservation precedes the claim, mirroring the legacy order, so a paced message never strands a row in `sending` under a live lease.
- **H9 (OPERATIONAL CONSEQUENCE WITHDRAWN — see H43; the primary claim STANDS) — `dead_letter` on the alerts path becomes crash-only (§6.5 row 16 narrowed).** Row 16 routes queue-retry exhaustion to `dead_letter`. After the R20 ack fix (§10.1 Residual 1) and H8, every consumer path that retries leaves the row `queued` — mode-off deferral, pacing wait, secret-read failure — and every classified outcome acks. A row can therefore only reach the DLQ while genuinely in flight, so the DLQ handler now spares a `queued` row in EVERY mode and dead-letters only a `sending` row (a crash between claim and outcome). ~~Consequence to expect operationally: a prolonged Slack outage no longer raises `dead_letter_present`; it raises `queued_backlog_stale`. Both are alarmed, so nothing becomes silent — but the runbook must read the second alarm as the outage signal.~~ **These two sentences are WITHDRAWN as false — see H43.** They follow only if a Slack outage manifested as a consumer RETRY path; it does not. An outage is POST-claim, so the row acks and lands `ambiguous`. The outage signal is `ambiguous_stale`.
- **H7 — the relay signing secret is REPURPOSED, not retired.** §6.6 retires the inbound-from-Slack surface together with `SLACK_RELAY_SIGNING_SECRET` and its rotation. The operator menu of §6.2/§6.3 needs an authenticated caller, and adding a binding or a secret would widen the surface for no gain, so the operator route (`POST /dispatch/operator`) signs with that same secret over a version-tagged canonical (`dispatch_operator_action_v1`, which domain-separates it from every legacy canonical). Consequence for F4: the secret and its two-slot rotation SURVIVE as the operator-console credential; only the Slack-facing endpoints and their canonicals are removed. F4's checklist therefore reads "retire the inbound-from-Slack endpoints and canonicals" rather than "retire the relay signing secret". If the operator console is ever moved behind an identity-aware proxy, this credential retires with it.

- **Residual 2 (OPEN) — the `changes() > 0` guard chain is proven only against the test harness.** `insertShadowPaired` (src/dispatch/wiring.ts) relies on `changes()` reflecting the immediately preceding statement of the same `batch()`, so that the shadow row commits only when the legacy insert actually inserted and the audit row only when the shadow row actually inserted. That behavior is currently exercised against the `node:sqlite` harness; it must be re-verified against real D1 during F2 before the parity gate is read as green. **Scope extended (F4/H12):** the same chain now also carries every operator mutation's UPDATE (src/dispatch/outbox.ts), which is bound by `changes() > 0` to its digest-guarded audit INSERT. The single F2 re-verification therefore covers two sites, and BOTH failure directions must be probed at the operator route, not only the repeated command: (a) too permissive — `changes()` reading non-zero when the audit INSERT was refused would restore exactly the read-then-act window H12 describes, never a transition of a different kind; (b) too strict — `changes()` reading zero when the audit DID insert would leave the audit row (it does not depend on `changes()`) with the UPDATE a no-op, so the route answers `409 delivery_state_conflict` with the digest already burned, contradicting H12's "a command whose CAS changed nothing writes no audit row, so it stays retryable"; recovery is a fresh timestamp (new signature ⇒ new digest), but the property is lost until then. The F2 probe list is therefore: one synthetic redelivered GUID through shadow ingress (orphan check), one repeated signed operator command (must 409 with a single audit row), and one ORDINARY signed operator command (happy path: the transition applies and its audit row lands).

- **H10 — the §6.3.1 escalation window is unreachable under resolver budget contention; a lifetime safety ceiling restores the §6.5 park.** §6.3.1 escalates an inconclusive row "after 6 attempts within 1 h → `manual`", and the implementation reads that literally: a WINDOWED count of the inconclusive `dispatch_audit` markers rather than the lifetime `resolver_attempts` counter. An adversarial panel over the uncommitted diff, independently confirmed by a refuter, proved that threshold unreachable BEFORE the branch was pushed. The mechanism is the resolver's own fairness: `ambiguousRowsDue` orders by `updated_ms ASC` and `incrementResolverAttempts` bumps `updated_ms`, so N due ambiguous rows round-robin strictly — one examination each per `ceil(N / slots)` passes. §6.7 fixes the cron at `*/5` (12 passes/h) and §6.3.1 fixes the budget at 2 rows per run, of which `runResolverPass` reserves `floor(2 / 2) = 1` slot for verification rows first, so ambiguous rows get 1–2 slots per pass. At **N = 6 with 2 slots, or N = 3 with 1 slot**, the per-row cadence reaches 15 min: at most 5 markers fall inside any rolling hour, the count saturates at 5, and 6 is never reached. The consequence lands in exactly the scenario §6.5 rows 15–16 describe ("live rows accumulate in `ambiguous` → resolver budget → `manual`"): during a prolonged outage NO row escalates — rows are alarmed as `ambiguous_stale` but never parked in `manual` with their evidence, and `manual` is the only gateway to the operator menu (`operatorResend` CASes from `manual`/`dead_letter`, `operatorCloseManual` from `manual`). **Fix.** The window stays the PRIMARY, fast trigger and a SAFETY CEILING is added beside it: `RESOLVER_LIFETIME_ATTEMPT_CEILING` (4 × `RESOLVER_MAX_ATTEMPTS` = 24) over the lifetime `resolver_attempts` counter. A row escalates when EITHER threshold trips, and a ceiling-triggered park carries `reason: "resolver_lifetime_ceiling"` plus `lifetime_ceiling` in its audit evidence, beside the unchanged windowed fields (`attempts`, `attempts_in_window`, `window_ms`), so the operator can tell the two escalation causes apart. **Rejected alternative.** Replacing the window with a lifetime ceiling of `RESOLVER_MAX_ATTEMPTS` ("whichever trips first" at 6) resurrects the very defect the window was introduced to fix — it parks a healthy row after six inconclusive scans spread across days. The RED "suppressed F5: six inconclusive attempts spread beyond the 1 h window do NOT escalate" pins that behavior and stays green unchanged, since its 6 lifetime attempts sit far below 24. **What is restored is reachability, not latency.** Time to the ceiling is `24 × ceil(N / slots) × 5 min` ≈ N hours at 2 slots (≈ 2N hours at 1 slot, and longer still when a history 429 sets `next_attempt_ms`), so a starved row parks hours after the §6.7 SLO for an escalated ambiguous row (< 10 min). That is accepted deliberately: the `ambiguous_stale` alarm still fires at 30 min, so the operator learns of the backlog long before any row parks; the ceiling exists to guarantee the documented terminal state is eventually reached, not to meet the SLO under contention.
- **H11 — the operator menu gains the R19 sweep (§6.2/§6.3.3 extended).** §6.3.3 declares that a duplicate materializing beyond the 24 h horizon is "never unrepairable: ANY later scan that observes a multi-match (including an operator-triggered sweep from the menu) applies the same repair (RED R19)", but the menu enumerated in §6.2 carries only `manual → queued` and `manual → closed_manual`. A row that acquires a duplicate AFTER both automatic scans is `delivered` with `verify_scans_remaining = 0` and `verify_after_ms` spent, and nothing in production could return it to the resolver's attention — R19 was reachable only from a test. `POST /dispatch/operator` therefore accepts a third action, **`sweep`**, under the same signed-request authentication (H7), the same freshness window and the same validation as the other actions. It CASes on `state = 'delivered' AND shadow = 0`, arms a scan (`verify_scans_remaining = MIN(verify_scans_remaining + 1, 2)`) AND stamps `verify_after_ms = now`; both halves are load-bearing, because `verificationRowsDue` selects on `verify_after_ms` and a counter without a due time leaves the row invisible to every resolver pass. **The increment is CLAMPED at the schema maximum**: migration 0010 CHECKs `verify_scans_remaining BETWEEN 0 AND 2`, and an operator-resent delivered row sits at exactly 2 — for the whole first-scan window, and INDEFINITELY while a §6.3.3/R18 inconclusive scan keeps deferring without decrementing, which is precisely when an operator reaches for this last-resort sweep. An unconditional `+ 1` violated the CHECK from that state, and the atomic batch rolled the audit row back with it, so the sweep armed nothing, left no trace, and reported a permanent state precondition as a transient `503 persistence_unavailable`. A bare clamp would in turn re-open F1 (the sweep's `verify_after_ms = now` can coincide with the due time a verification pass already in flight observed, and from counter 2 an unchanged counter would leave BOTH halves of that pass's completion CAS matching — consuming the operator's fresh scan), so the clamp is paired with a **change-guaranteeing predicate**, `AND (verify_scans_remaining < 2 OR verify_after_ms IS NOT :now)`, carried identically by the UPDATE and its audit statement. The sweep therefore always moves the counter or the due time, never neither: below the maximum the counter increments, so a stale pass's expected counter cannot match; at the maximum the due time necessarily moves, because the only case where it would not is the one the predicate rejects. **What the sweep guarantees is thus: at least one scan armed and due now, clamped at the schema maximum of 2.** The single rejected case — already at 2 AND already due at exactly this instant — is a genuine no-op (the row is already armed and already due) and answers 409, never 503. The sweep performs NO Slack egress and publishes nothing — the next resolver pass runs the §6.3.3 match rule and applies the §6.3.2 repair. A row that is not `delivered` answers 409. I1 is untouched: a sweep can only delete later copies, never create a message.
- **H12 — every operator command is one-shot (§6.2/§6.3 I1 tightened).** H7's signed canonical carries a freshness timestamp, which bounds replay to five minutes but does NOT make a non-idempotent command single-use: if a resend returns the row to `manual` quickly and the caller retries the identical signed request after a lost response, the same command is accepted again and initiates a SECOND resend — an operator-marked possible duplicate the operator never approved. Each operator transition therefore bakes the SHA-256 of its request signature into its `dispatch_audit` evidence (`request_signature_sha256`), and the route refuses a command whose digest is already recorded for that delivery with `409 already_applied` before executing anything. No schema column is added: the audit journal IS the applied-command ledger. **Trade-off, stated rather than hidden:** the command is one-shot for the lifetime of `dispatch_audit` — the whole retention of that table — and no longer than that; if audit rows are ever pruned, replay protection ends with them and reverts to the five-minute freshness window. A command whose CAS changed nothing (409 `delivery_state_conflict`) writes no audit row — the audit INSERT shares the CAS predicate — so it stays retryable once the row is eligible again, which is the intended behaviour and not a hole in the rule. **Amended (Copilot suppressed finding F4, review 4943164344).** The claim that "the store CAS still bounds the damage of the simultaneous case to one transition" is WITHDRAWN: it is false for `sweep`. Two simultaneous identical requests both observe no digest, and on a `delivered` row with zero scans the first sweep increments 0 → 1 while the second still satisfies H11's predicate (`verify_scans_remaining < 2`), increments 1 → 2 and applies the same command a second time. The digest is therefore CONSUMED inside the mutation: every operator mutation (`resend`, `close_manual`, `sweep`, `mark_delivered`) carries it into its own `batch()`, where the audit INSERT — the applied-command ledger row itself — refuses a digest already recorded for that delivery (`actor = 'operator'`, the same scope the pre-check reads), and the UPDATE is bound to that one decision by `changes() > 0`; both statements therefore apply together or not at all, and two concurrent identical commands apply exactly once. Still no schema column. The route's read-then-act check survives ONLY as the fast 409 path. Why the guard is not the same `NOT EXISTS` on both statements: a `batch()` is one transaction on one connection, so the UPDATE would observe the audit row that same batch had just inserted and would never fire (probed empirically before implementing), and the audit INSERT cannot move after the UPDATE because it reads `from_state` from the live row. **Trade-off, unchanged in kind:** the binding lasts exactly the retention of `dispatch_audit`; and the UPDATE half now shares the `changes()`-chain caveat of Residual 2 below.
- **H13 — the menu carries the §6.2 `manual → delivered` transition.** §6.2 lists "`manual → delivered` (operator marks with ts evidence…; audited)" among the permitted transitions, and §6.9 option (b) depends on it, but the route exposed no action for it, so a row whose message the operator located by hand could only be closed WITHOUT its canonical identifiers. The action **`mark_delivered`** applies that transition with an operator-supplied `slack_message_ts` and `slack_channel_id`, both validated against the exact shapes migration 0010 CHECKs (the same patterns the §6.2 classifier applies to a `chat.postMessage` body — malformed values are `400`, never a constraint violation) and both included in the SIGNED canonical, so an intercepted command can never have its recorded ts swapped. The transition CASes from `manual` only (409 otherwise), is audited with actor `operator` and the operator's evidence string, performs no Slack egress and publishes nothing. It arms NO §6.3.3 verification: it records proof of a message that already exists, not a resend, so it creates no duplicate risk and needs no scan — H11's sweep is the path for re-checking such a row later. I1 is unaffected: the only resend path remains `manual → queued`.
- **H14 — the non-exhausted verification scan had no exit and no alarm; the re-arm becomes bounded, terminating and visible (§6.3.3 extended).** §6.3.3 runs each verification scan "over the full window (row `created_ms − 300 s` → now)" and `completeScan` is gated on pagination exhaustion (§6.3.1). A scan that ends with a live cursor therefore lands on `flagDuplicateRepairPending`, which re-armed the row at a FLAT `verify_after_ms = now + 15 min` — no backoff, no cap, no ceiling. Three properties made that a silent livelock rather than a retry: the window's far end is `now`, so it grows while the budget (3 pages × 200 messages) does not, and once channel traffic inside it exceeds ~600 messages no scan can ever exhaust; `verify_scans_remaining` decrements only through `completeScan`, so the row never leaves the due set; and `observer.ts` had no condition matching a livelocked `delivered` row, so nothing was ever alarmed. The row re-scanned every 15 minutes for ever, consuming the reserved verification slot of every cron pass, with no operator exit (`operatorCloseManual` CASes from `manual`, and a sweep only re-arms). **Fix.** Every re-arm that made NO PROGRESS — a partial scan, a failed history read, a scan with no match, a failed `chat.delete` — now shares ONE bounded backoff (the §6.3.3 first-scan delay doubled per consecutive no-progress scan, capped at 24 h, the ladder the deferral path already used) and ONE streak, counted as the trailing run of `no_progress` audit markers. After `VERIFY_NO_PROGRESS_CEILING` = 8 the row STOPS re-arming: it stays `delivered`, keeps `verify_scans_remaining` as evidence, has `verify_after_ms` cleared (which is what removes it from `verificationRowsDue`), records a distinguishable `verification_abandoned` audit marker, and raises the new observer alarm `verification_abandoned` — derived from the row shape, so an operator sweep clears it. H11's sweep restores the row to the resolver's attention with a fresh streak (the abandon marker carries no `no_progress` field, so it breaks the run), which keeps R19 ("no duplicate is ever unrepairable") intact: what is bounded is the AUTOMATIC retrying, never the repairability. **Why ONE streak and not one per marker kind.** A streak per kind resets the other: an alternating sequence — partial scan, then a history 429, then partial again — is the normal shape on a busy channel, and neither counter would ever reach its ceiling, so the livelock would have survived the fix. **Rejected alternative, recorded because it was the proposed fix.** Bounding the verification window at the row's own `slack_message_ts` (on the premise that a duplicate can only exist at or after the canonical instant) was REJECTED: the premise is inverted for exactly the population that runs verification scans. Verification is armed only by an operator resend, a detected pending duplicate or an operator sweep, so every verification input is a row with prior attempts — and a row that reaches `manual` through `resolver_budget_exhausted` (§6.5 rows 15–16, §10 H10) was never proven absent, so a copy from an EARLIER attempt may exist at a ts BELOW the resend's. That bound would have made such a copy permanently invisible and would have turned §6.3.2's "the EARLIEST ts is canonical" repair (`updateCanonicalTs` from a verification scan) into dead code — trading a silent correctness loss for exhaustion feasibility. The ceiling alone terminates the loop, and it bounds the window growth with it, because the number of scans is now finite. **Operational consequence to expect:** on a channel busy enough that the window can never be exhausted, a verification eventually parks with `verification_abandoned` instead of completing; the runbook reads that alarm as "run the H11 sweep, or verify by hand".
- **H15 — `dead_letter` requires an EXPIRED lease, and the cron stops republishing the same stale row on every pass (§6.5 row 16 and H9 narrowed).** H9 already reduced the DLQ transition to "only a `sending` row (a crash between claim and outcome)", but `markDeadLetter` CASed on `state IN ('queued','sending')` with no lease term, and its only caller decides from a bare read-then-act snapshot. Duplicate DLQ arrivals are not exotic: the cron republished EVERY stale `queued` row on EVERY pass (the republish changed nothing on the row, and `staleQueuedRows` selects on `updated_ms` alone), so the same row was re-published until it left `queued`. Two consequences followed: a row in `sending` under a LIVE lease — a send genuinely in flight — was dead-lettered mid-flight; and an operator resend landing between the handler's read and its write was dead-lettered too, recording the `queued → dead_letter` transition H9 declares impossible. **Fix.** The predicate now encodes the handler's decision: `state = 'sending' AND lease_until_ms IS NOT NULL AND lease_until_ms < now`, carried identically by the UPDATE and its audit statement. A live-lease arrival is acked and the row is left alone; if that send does crash, lease expiry hands the row to the resolver (§6.3.1 normalization → `ambiguous`), which is the SAFER of the two outcomes — evidence and a verdict instead of a terminal park. A `queued` row is now spared by the store, not merely by the caller's snapshot. **The amplifier is reduced, not removed:** a successful republish stamps `updated_ms`, so a stale row returns at most once per `STALE_QUEUED_REQUEUE_AFTER_MS` instead of once per pass; with the `*/5` cron and a 5-minute threshold that is roughly a halving, not an elimination — R13 keeps re-entering the row until it leaves `queued`, and Cloudflare Queues remain at-least-once by construction. The actual protection against a duplicate arrival is the claim CAS (R1) plus this predicate. That stamp is the ONE mutation in `src/dispatch/outbox.ts` that writes no audit row, deliberately: it changes no state and carries no decision, and auditing it would append a row per stale row per cron period for ever — precisely the R20 mode-off shape ("rows accumulate in `queued`"), so the journal would grow without bound while recording nothing.
- **H16 — an expired SHADOW lease normalizes to `queued`, not `ambiguous` (§6.3.1 and §6.5 row 10 excepted).** §6.3.1 states unconditionally that a `sending` row with `lease_until_ms < now` is CASed to `ambiguous` with a `lease_expired` audit, and §6.5 row 10 repeats it. `normalizeExpiredLeases` splits on the `shadow` flag: a real row takes that rule verbatim, a shadow row returns to `queued` with a `lease_expired_shadow` audit. The behavior is correct and was deliberate — §9.A1 removed all shadow egress, so a shadow row never called Slack and there is nothing ambiguous about it; sending it into the `ambiguous` path would put a row that provably posted nothing in front of the resolver, spend history scans and the per-run budget on it, and (with no message to find) drive it toward a `manual` park that no operator action fits. Returning it to `queued` lets the cron's inline shadow processing complete it off-queue. Nothing in the ratified text permitted the exception, so it is recorded here rather than left as an undocumented divergence. No code changed with this amendment.
- **H17 — an operator sweep deliberately restarts the verification horizon (§6.3.3 clarified).** §6.3.3 schedules the two scans at `delivered_at + 15 min` and `delivered_at + 24 h`, but there is no `delivered_at` column (§6.4 stores no such field): `completeScan` derives the second scan from the row's CURRENT due time (`verify_after_ms − 15 min + 24 h`). `operatorSweepVerification` (H11) stamps `verify_after_ms = now`, so a sweep taken between the two scans moves the second one to `sweep_time + 24 h` rather than `delivered_at + 24 h`. Of the two available fixes — persisting a stable `delivered_at` anchor, or recording the drift as deliberate — the record is chosen, for three reasons: the drift only ever moves the horizon LATER (a deferral or a sweep pushes the due time forward, never back, so no scan is skipped or pulled into the cooling-off window); it is what an operator asking for a fresh look actually wants, since the sweep exists to re-open a row's verification and a 24 h re-check counted from that moment is the useful one; and the alternative would add a column to migration 0010 plus a write on every delivery to remove a divergence with no failure mode attached to it. R19 is untouched either way: any later scan applies the same repair. No code changed with this amendment.
- **H18 (SCHEMA CLAUSE SUPERSEDED by H39; the read-scoping fix STANDS) — the dispatcher's aggregates are SCOPED to the destinations it owns; H3's "inert" claim is corrected (§6.7 narrowed).** Migration 0010 CHECKs `destination IN ('alerts','activity')` while H2 reduced the dispatcher to `alerts`, and `DispatchDestination` is the single literal `"alerts"`. `statusCounters` built its per-state map from that union — `{ alerts: … }` — but its grouped query read EVERY destination in the table and then did `byStateAndDestination[entry.destination][entry.state] = n`. A schema-valid `activity` row therefore threw `TypeError: Cannot set properties of undefined`, which is a `503` on `/status` (the route wraps the call) and an ABORTED cron pass (`runDispatchCronPass` opens with the same call, before the stale-queued republish, the resolver and the observe-only alarms). The row need not be exotic: the schema RED for `UNIQUE(destination, slack_message_ts)` inserts exactly one. **Fix.** All four aggregates — the grouped per-state counters, the oldest non-terminal age, the oldest ambiguous age and the abandoned-verification count — carry `destination IN (…)`, bound from the counter map's OWN keys, so the query can no longer return a destination the map lacks; that missing invariant is the whole defect. - **H19 — the pacing reservation is taken only for a row OBSERVED `queued` (H8 narrowed).** H8 reserves a send slot "before each claim". The implementation gated that on `!row.shadow` alone, so a REDELIVERED message for a row already in `sending`, `ambiguous` or `manual` — routine, since Cloudflare Queues are at-least-once and §6.5 case 11 expects duplicate deliveries — consumed the shared per-destination reservation and only then discovered, through the claim CAS, that there was nothing to send. Nothing was posted, yet the next genuinely queued alert was pushed a full `DISPATCH_MINIMUM_SEND_INTERVAL_MS` (6.1 s) behind a phantom reservation, and a burst of redeliveries could pace the channel to a standstill without a single message going out. **Fix.** The reservation is taken only when the row is observed `queued`; every other non-terminal state falls straight through to the claim, which no-ops and acks exactly as before (§6.5 case 11). This is NOT a claim: the read is advisory and the claim CAS still decides, so a row that leaves `queued` between the two is handled as it always was. Shadow rows stay exempt (§9.A1).
- **H20 — the duplicate-repair re-arm carries the caller's snapshot (§6.3.2/§6.3.3, completing the F1/B7 guard family).** `completeVerificationScan` (Copilot F1) and then `deferVerificationScan` and `abandonVerification` (audit B7) all CAS on the due time their caller observed. `flagDuplicateRepairPending` — the third no-progress writer, reached from a partial scan, a failed `chat.delete` or a lost found_many CAS — did not. An operator sweep (H11) landing after the pass's read stamps `verify_after_ms = now` precisely to force a due-NOW scan; the stale pass then overwrote it with `now + backoff`, postponing the scan the sweep promised by up to 24 h and leaving the operator with no signal that their command had been undone. **Fix.** The observed due time AND the observed counter both join the CAS. Both halves are load-bearing because H11's change-guaranteeing predicate moves the counter OR the due time and never neither: below the schema maximum the sweep increments the counter (so a counter-only guard would catch it, a due-time-only guard would not), at the maximum it necessarily moves the due time (so the converse holds). The audit row shares the predicate, so a refused re-arm leaves no pending marker either (§6.1). **Which snapshot, and one bounded residual.** On the VERIFICATION path the pass-start row is the observation and must stay so — re-reading before the write would adopt the very sweep the guard exists to protect, which is the defect. On the AMBIGUOUS path this pass's own `markDelivered`/`recordLateProof` legitimately stamps `verify_after_ms` (§6.3.3), so the pass-start value is stale BY CONSTRUCTION rather than by race, and the observation is re-read after that write. A sweep landing between that write and that re-read is still overwritten; closing that microsecond would require `markDelivered` to return the stamped due time, which is not worth widening a store signature used by four call sites. The loss is bounded to the sweep's due-now scan, and R19 is untouched: the re-arm this call writes is itself a future scan, and any later scan applies the same repair.
- **H21 — every duplicate deletion is INTENDED durably before the call and reconciled after it (§6.3.2 extended).** §6.3.2 requires every deletion to be audited, and the `repaired_duplicate` marker was written AFTER `chat.delete` returned. `chat.delete` is the dispatcher's one IRREVERSIBLE egress: when it succeeds the `ts` is gone from Slack, so a worker termination — or any D1 failure — between the call and the marker destroyed the evidence permanently. No later history scan can rebuild it, because the evidence such a scan looks for is exactly what was deleted; the row's own state is unchanged, `repairedDuplicatesTotal()` stays flat, and nothing is alarmed. The B4 behaviour ("a failed audit is reported as not repaired, the cost is one uncounted marker") described that as a counting loss; it is in fact an AUDIT loss, and §6.3.2 does not permit it. **Fix, without a new table — the audit journal is the ledger, as it already is for H12's digests and H14's streak.** The resolver appends a `duplicate_deletion_intent` marker BEFORE the call; a failure there returns "not repaired" WITHOUT calling Slack (fail-safe in the other direction — the copy survives and R19 repairs it later). After the call the intent is reconciled: `repaired_duplicate` when the deletion succeeded, `duplicate_deletion_not_applied` when it did not, both carrying the same `target_ts` correlation key the intent carries. `unreconciledDeletionIntents` counts intents with no later outcome for that ts, `statusCounters` exposes it and the observer raises **`duplicate_deletion_unreconciled`** — so the one interleaving whose evidence cannot be rebuilt is counted and alarmed instead of silent. A later successful repair of the same ts reconciles an older dangling intent by construction (`seq >` plus the shared key), so a crash BEFORE the call self-heals on the next scan. **One consequence recorded deliberately:** the two bookkeeping markers are NEUTRAL for H14's no-progress streak — they are written between the scan and its re-arm, so counting them as progress would reset the streak on every pass of a row whose `chat.delete` keeps failing and would restore exactly the unbounded livelock H14 closed. The completion marker is NOT neutral: a deleted copy is real progress and resets the streak, as it always did.
- **H22 — `mark_delivered` requires the dispatcher's CONFIGURED channel, not merely a well-formed one (H13 narrowed).** H13 validates the operator-supplied `slack_channel_id` "against the exact shapes migration 0010 CHECKs". Shape is not identity: a well-formed id for ANY other channel — `#github-activity`'s (C0BMQMW3L4E) included, which H1 hands to the official app — was accepted, and the row then carried canonical proof pointing outside the dispatcher's own channel. `slack_message_ts` is unique only per channel, and every later reader resolves the channel from the row's DESTINATION (`channelForDestination`), so an H11 sweep or a §6.3.1 scan would search `#github-alerts` for a ts that lives elsewhere, find nothing, and treat a delivered row as unverifiable. **Fix.** The route requires `slack_channel_id` to EQUAL the configured channel of the dispatcher's single destination (H2) and answers `400 channel_not_dispatcher_owned` otherwise — before any mutation, so the signature digest is not burned and the command stays retryable with a corrected channel. The check lives at the route rather than in the parser so the refusal carries its own machine-readable code instead of the generic `invalid_request`. The operator-supplied `ts` keeps SHAPE validation only, deliberately: there is no stored value to compare it against (that is the point of H13), it is inside the signed canonical, and H11's sweep is the path to re-verify such a row.
- **H23 — §6.3.1 lease normalization never waits on a secret (§6.7 cron ordering).** Normalization is a D1-only transition — `sending` with an expired lease becomes `ambiguous`, or `queued` for a shadow row (H16) — and needs no Slack credential. It ran INSIDE `runResolverPass`, i.e. after the cron had already awaited `readBotToken()`, so a Secrets Store outage skipped it entirely: a send that crashed between claim and outcome stayed `sending`, invisible to the `ambiguous_stale` alarm computed later in the same pass, and a SHADOW row that needs no token at all never returned to `queued`. The one moment egress credentials are unavailable is exactly when that visibility matters most, and §6.7's observe-only guarantee (R5, suppressed F3) is void if the rows never reach the states the alarms watch. **Fix.** The cron normalizes FIRST, before any secret read, and then decides from the POST-normalization DUE set — `ambiguousRowsDue` and `verificationRowsDue` — whether resolver egress, and therefore the token, is needed at all. Rows that just became `ambiguous` are included by that decision; a backlog deferred by a recorded Retry-After (§6.2/R4) costs no secret read, where the previous counter-based gate read the token for rows the resolver could not have examined. `runResolverPass` keeps its own normalization where §6.3.1 puts it (a no-op by then, and its direct-call contract is unchanged). **Residual, recorded rather than hidden:** the QUEUE consumer's adapter still reads the token before processing any non-`off` message, so a shadow row's queue message is retried during an outage even though its processing needs no token. That work is not lost — the cron's inline shadow processing drains it off-queue (§9.A1) and R13 republishes — and closing it would mean making `botToken` lazy across the consumer contract; it is recorded here instead of being fixed silently.
- **H24 — a Retry-After is validated AFTER the millisecond conversion, and bounded by the legacy ceiling (§6.2 [E-A12] and §6.3.1/R4 tightened).** Both readers of the header — the §6.2 classifier and the resolver's history scan — checked `Number.isFinite` on the parsed SECONDS and only then multiplied by 1000. `Retry-After: 1e308` is finite as seconds and `Infinity` as milliseconds, so an infinite delay was persisted: `next_attempt_ms` left an ambiguous row permanently undue for the resolver, on the very path (R4) whose purpose is to make it due LATER, and `verify_after_ms` did the same to a verification row WITHOUT ever raising `verification_abandoned`, because H14's ceiling counts only scans that actually run. A total, fail-safe classifier (§6.2) cannot emit a value that unreachable. **Fix.** The CONVERTED value is what is validated: a non-finite result is treated as an ABSENT header — the §6.2 fail-safe for a value that cannot be trusted, so each caller falls back to its own bounded backoff (the resolver's `noProgressDelayMs`, or an immediately-due ambiguous row exactly as with no header at all) — and a finite value above `RETRY_AFTER_CEILING_MS` is CLAMPED to it. That ceiling is the legacy path's own bound verbatim (`retryAfterSeconds`, src/index.ts: `Math.min(43_200, …)` seconds = 12 h), not a new invention, so both paths schedule inside one envelope. The resolver no longer keeps a second copy of the conversion: it imports the classifier's, the same "one shape, one source" rule the canonical-ts pattern already follows.
- **H25 — the canonical-ts repair carries the caller's OBSERVED ts (§6.3.2, completing the E1 sweep).** `updateCanonicalTs` CASed on `state = 'delivered' AND shadow = 0` only, while its caller decides from the ts it observed (`row.slackMessageTs` on the verification path, the re-read `fresh.slackMessageTs` after a lost found_many CAS). A pass whose scan was PARTIAL could therefore overwrite an EARLIER canonical ts that a fuller concurrent scan had just recorded, regressing the row to a later copy — the inverse of §6.3.2's "the EARLIEST ts is canonical" — while the deletion loop's "never delete the recorded ts" filter went on using the stale observed value. **Fix.** The observed ts joins the CAS (`slack_message_ts IS ?`, NULL-safe), carried identically by the UPDATE and its audit statement. A concurrent repair's ts survives; the refused pass simply records nothing, and R19 keeps any residual repairable by any later scan. This was found by the E1 enumeration (every mutating store method versus the snapshot its callers decide from) rather than by review, and it is the last such gap: with H20 and H25 in place, every CAS in `src/dispatch/outbox.ts` either encodes the values its callers decided from or is a blind, self-guarding command whose predicate defines the precondition on its own.

- **H26 — §6.7 ratified an alarm PREDICATE and never a delivery channel; the gap is declared, not closed here.** The observe-only job computes its alarm set on every cron pass and emits each one as a structured `console.error` line. Nothing consumes those lines: no workflow polls them, no channel receives them, and `/status` is a pull surface nobody pulls. §6.7 specifies exactly when to alarm and is silent on how an operator LEARNS of it, so the artifact is faithful to the clause and still leaves the operator blind unless they go looking — a gap no code review could surface, because every line involved is correct. It was found by asking, from the operator's seat, what a bad week actually requires. **Deliberately NOT closed in F1**, for two reasons: the dispatcher is inert at `DISPATCH_MODE=off`, so there is nothing yet to be blind to; and the obvious channel — posting the alarm to `#github-alerts` through the dispatcher — is the self-referential trap this whole redesign exists to kill (defect D12 of the retired system: alerts about the alerting system routed through the alerting system). **F3 therefore gains an explicit step:** choose and wire a delivery channel that does not depend on the dispatcher, using an official mechanism (a scheduled GitHub workflow reading `/status` and failing loudly, or a Cloudflare notification on the Worker's logs), and record the choice here. - **H27 — the canonical-ts repair may only move the recorded ts EARLIER, unless the scan exhausted (§6.3.2 tightened; corrects H25).** H25 gave `updateCanonicalTs` a CAS on the caller's observed ts, but the CALLER still chose the value the same way: the earliest ts of THIS scan. `conversations.history` returns newest-first, so a scan stopped by the 3-page budget sees exactly the LATER copies; a row already holding canonical proof `A` on an unseen older page was therefore rewritten to `B` — the direct inverse of "the EARLIEST ts is canonical" — after which the deletion loop removed only copies later than `B`, leaving BOTH the original message and the newly recorded one alive, and repeated partial scans could reach `verification_abandoned` (H14) without ever restoring the true canonical. **Fix.** The recorded ts is updated only when the candidate is provably EARLIER than the stored value (compared as decimal strings through the existing `compareSlackTs`, never as JS numbers), **or** when the scan EXHAUSTED. Exhaustion is what separates "unpaged" from "gone": a complete census that does not contain the recorded ts proves that message is no longer in the channel (§6.5 row 17, or a ts recorded by hand through H13), so the earliest surviving copy legitimately becomes canonical and every later copy is deleted — the repair CONVERGES to one message instead of stalling. On a PARTIAL scan the earliest OBSERVED copy is additionally spared from deletion and reported pending: `chat.delete` is irreversible (H21) and a partial scan cannot yet tell the two cases apart, so the fail-safe direction is to leave a copy alive and let the scan that does exhaust settle it. The EFFECTIVE canonical — not the raw scan minimum — is what the audit evidence, the deletion loop's never-delete filter and the returned verdict now carry.
- **H28 — a lost canonical-ts CAS aborts the deletion pass (§6.3.2; completes H25).** The boolean `updateCanonicalTs` returns was IGNORED at both repair sites. - **H43 — the prolonged-Slack-outage signal is `ambiguous_stale`, NOT `queued_backlog_stale` (corrects H9's operational consequence; §6.5 row 16's surviving clause).** H9's last two sentences — quoted and struck through above — say a Slack outage raises `queued_backlog_stale` and instruct the runbook to read it as the outage signal. They are WITHDRAWN as false. H9 states both of its own premises correctly ("every consumer path that retries leaves the row `queued`" AND "every classified outcome acks") and then draws a conclusion that follows only if an outage manifested as a consumer RETRY path. It does not. **The enumeration.** Of the eleven non-shadow outcomes of a send attempt, NINE are `ambiguous` (fetch throw — TLS/DNS/socket, or the 30 s abort; HTTP 429; HTTP 5xx; unexpected 3xx/4xx; 200 with an unparseable body; 200 `ok:true` with malformed canonical identifiers; 200 `ok:true` without a ts; 200 `ok:false` with a non-manual code; 200 of unrecognized shape), one is `delivered` and one is `manual`. NOT ONE leaves the row `queued`, and every one of them ACKS. A Slack outage is made exclusively of those ambiguous outcomes, all of them POST-claim; with no automatic resend (I1), the rows accumulate in `ambiguous` and the first one is >30 min stale 30 minutes into the outage. This is a self-contradiction INSIDE §10, not a doc-vs-code drift: H10, which postdates H9, already says "rows are alarmed as `ambiguous_stale`" during a prolonged outage, and §6.5 row 16's Recovery cell already says "live rows accumulate in `ambiguous`". Neither alarm covers the claim-CAS no-op ("lease unavailable"): that row has already LEFT `queued` and nothing accumulates. **Why the old text was operationally dangerous, not merely wrong.** During a real outage `queued_backlog_stale` is CONDITIONAL (it needs a nonzero `queued` count at the snapshot instant) while `ambiguous_stale` is GUARANTEED; the operator was watching the alarm that may not appear, and was told the one that certainly appears meant only "check whether Slack is degraded". In the other direction, `queued_backlog_stale` fires on mode-`off` accumulation, on a Secrets Store failure and on a pacing backlog, so reading it as "Slack is down" sends the operator to Slack's status page when the fault is in the token binding or the mode flag — which is why the runbook's first action for that row now names those two first. **No code and no clause of §6 changes for this amendment:** it is the ADR and the runbook catching up to §6.5 row 16 and to H10. Secondary observation that does NOT rescue H9's mechanism: with `max_batch_size 1`/`max_concurrency 1` and a 30 s abort per message, a timeout-flavoured outage serializes the consumer at ~1 message per 30 s, so queued rows CAN accumulate and the queued alarm CAN co-fire — a throughput consequence conditional on ingress volume, not the "every waiting path leaves the row queued" mechanism H9 asserts.
