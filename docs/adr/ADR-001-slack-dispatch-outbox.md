## 2. Verdict

**Recommendation, confirmed by the analysis below: retire the reconstruction design, with a precise cut.** The causal chain rests on documentation facts and code structure:

- (a) the chosen Slack primitive (webhook trigger) is documented to answer only `{"ok": true}` with no execution/invocation ID [E-A8];
- (b) no documented API exists to query or cancel a specific execution from data passed into the trigger [E-A10 — absence verified];
- (c) to recover correlation, the system promoted `apps.activities.list` (an activity-log API restricted to workflow apps, retention undocumented [E-A9]) into the mechanism that reconstructs delivery truth;
- (d) that required a temporal checkpoint coupled to ownership, hydration and readiness — three checkpoint writers share a duplicated clamp SQL [E-C1] plus two more clamps monitor-side [E-C4];
- (e) the resulting machine carries a 10-state delivery enum [E-C3] and 6 auxiliary tables, and produced the records of §1.

**What is KEPT (not rewritten):** webhook ingress with HMAC verification, event allowlist, normalization, and dedup by GitHub delivery GUID (`INSERT ... ON CONFLICT(delivery_id) DO NOTHING` [E-C6]); the queue topology (alerts/activity + DLQs); D1 as the durable store; the "GitHub Slack Webhook Redelivery" workflow. GitHub's delivery GUID is documented as stable across redeliveries [E-A7], so redelivery + dedup is safe by construction.

**What is REPLACED entirely:** the egress path (Slack Workflow triggers, receipts, `/slack/progress`), the reconstruction monitor, and the entire checkpoint/hydration/scan/reconciliation machinery.

## 3. Defect inventory (properties of the code at SHA 2c329cd1, each evidence-linked)

- D1 frontier×hydration coupling: any pending hydration freezes the frontier (monitor: `reportCheckpointUs = hasPendingHydration ? previousCheckpointUs : evidenceCheckpointUs` [E-C4]).
- D2 duplicated clamp in the Store: checkpoint advance also blocked by any `slack_trace_hydration_registry` row whose status column holds `pending` [E-C1].
- D3 delivery clamp is separate and load-bearing: it protects the two ambiguous delivery rows and cannot be silently removed [E-C1].
- D4 global state can diverge from the locally-hydrated subset (budget of 2 trace hydrations per run vs. global pending count).
- D5 no safe automated recovery path exists for `accepted_by_trigger` (2xx received, no receipt/trace/ts — resend may duplicate, advancing may erase the correlation window).
- D6 the monitor acts as source of truth: it reconstructs and mutates ownership, delivery rows, checkpoint, debt, manual review and replay.
- D7 the delivery clamp is broader than its documentation: `OR slack_trace_id IS NULL` pins the checkpoint on ANY non-legacy row without an attached trace — including `delivered` rows confirmed via receipt and `manual_review`/`dead_letter` rows [E-C1].
- D8 ~700 lines of dead Store code: `recordSlackTrace`, `resolveSlackTraceIdentityBySendExecutionId`, `getSlackActivityCheckpoint`, `finalizeSlackReconciliationReport`, `advanceSlackActivityCheckpoint` sit on the interface and have no caller in `index.ts` [E-C7] — two parallel implementations of the same resolution semantics kept in sync by hand.
- D9 unreachable version bridges: the worker keeps v2–v4 parsers only to answer `409 reconciliation_upgrade_required`; the monitor carries full v2–v4 client paths although the checkpoint endpoint always answers `reconciliation_version: 5` [E-C7].
- D10 a byte-exact protocol seal on the hot path: D1 triggers freeze `relay_state` by byte identity; every queue message, cron and health check re-reads `sqlite_schema`; the seal validates only the FORMAT of `WORKER_VERSION.tag` (any 40-hex passes), not the deployed revision.
- D11 by design, the readiness probe and the monitor merge three distinct concerns — liveness, readiness and alerting — into single fail signals: the probe SQL [E-C2] maps ANY `manual_review`/`dead_letter` row, overdue receipt or hydration-debt row onto the unavailable response of the kind recorded in [E-E1], and the monitor's code path [E-C5] throws the exact error recorded in [E-E2] even when its own durable reconciliation ended without error. Consequence of the design: operational debt has no representation other than making the whole probe/scheduled job fail ("infinite red"), which the prior review round had already objected to.
- D12 self-referential alerting: the payload recorded for delivery `d43b2d70` [E-B] is itself an alert about the `slack-production` environment (event `deployment_status`) — the design routes alerts about the system's own troubles through that same system.
- D13 secret rotation left mid-state (`SLACK_RELAY_SIGNING_ACTIVE_SLOT: "next"` pinned in wrangler config and in the monitor job env; the GH secret named `SLACK_RELAY_SIGNING_SECRET` injected as env `..._NEXT`) and hardcoded identifiers (channel IDs, worker hostname, Slack function IDs) across worker, monitor and Slack app.
- D14 three time units on the critical path: ms (`updated_at`), µs (checkpoint; `updated_at * 1000` in the clamp SQL [E-C1]), unix-seconds strings (`relay_timestamp`).

## 6. New design

### 6.1 Data flow
GitHub webhook → ingress (HMAC, normalize, presence fence per §6.8, `INSERT dispatch_outbox state='queued'` keyed by GUID; the INSERT and — in F2 — the old-path insert commit in ONE `batch()`; queue publish follows the commit) → consumer: CAS claim `queued → sending`, recording `last_send_start_ms`, lease 90 s (0 rows changed ⇒ duplicate ⇒ ack) → `chat.postMessage` with `metadata.event_payload.delivery_id`, **hard client timeout 30 s (abort)** → outcome classified by §6.2's total classifier, applied in one `batch()` with an audit row. Plain top-level message only: the dispatcher never sets `thread_ts`/`reply_broadcast` (R15).

### 6.2 Total outcome classifier and state machine (single writer = the worker)
**Classification precedence: the HTTP status is classified first; `ok`-body rules apply ONLY to HTTP 200 responses.**
- HTTP 200, `ok:true`, `ts` → `delivered` (canonical proof).
- HTTP 200, `ok:false` with a code in the MANUAL list — `invalid_auth`, `token_revoked`, `account_inactive`, `missing_scope`, `channel_not_found`, `not_in_channel`, `is_archived`, `restricted_action`, `msg_too_long`, `no_text`, `invalid_blocks`, `invalid_metadata_format`, `invalid_metadata_schema`, `metadata_too_large`, `metadata_must_be_sent_from_app`, `message_limit_exceeded` → `manual` (deterministic config/payload failure; automatic retry cannot succeed; no automatic resend ⇒ no duplicate risk).
- HTTP 200, `ok:false` with `internal_error`, `fatal_error`, or ANY code not in the MANUAL list → `ambiguous` (the descriptions do not state whether effects were applied [E-A15] — fail-safe).
- HTTP 429 (regardless of body, including an `ok:false ratelimited` body) → `ambiguous`; the `Retry-After` value is recorded and honored by the resolver's scheduling [E-A12].
- Everything else — unexpected 3xx/4xx, 5xx, network timeout (including our own 30 s abort), TLS/DNS/socket failure, malformed or non-JSON body — → `ambiguous`.
- Worker crash after send: lease expiry makes the row resolver-input.
**There is NO automatic resend of any kind — the state `retry_scheduled` does not exist.** Further transitions: `ambiguous → delivered` (resolver FOUND); `ambiguous → manual` (resolver PROVEN-ABSENT, carrying its full evidence; or resolver budget exhausted, inconclusive); `manual → delivered` (operator marks with ts evidence, or a late canonical `ok:true` + `ts` from a previous attempt arrives — proof beats inference; audited); `manual → closed_manual` (audited closure without resend); `manual → queued` (the ONLY resend path: explicit operator action, marked possible-duplicate, arming §6.3.3 verification); queue-DLQ exhaustion → `dead_letter` (alarmed; operator menu). Ambiguity is first-class and never resolves silently.

### 6.3 Idempotency contract (invariant I1)
PK = GitHub delivery GUID end-to-end; transport at-least-once; effect deduplicated by CAS claim. **I1 — a resend may be initiated ONLY by the operator, via the audited menu, marked possible-duplicate. The resolver's verdicts are EVIDENCE presented to that decision, never triggers. The system never creates a possible duplicate by itself.** The complete duplicate surface is therefore exactly ONE case: an operator-accepted possible-duplicate — and even it is guarded: the operator resend arms the §6.3.3 verification scans, and any materialized duplicate is detected and repaired (§6.3.2), audited and alarmed. Server-side late materialization having NO documented latency bound [E-A16] is thereby rendered harmless: with no automatic resend there is nothing for a late post to race against except an explicit human decision that was made knowing the risk. **Late-proof rule:** if a consumer receives `ok:true` + `ts` after its `WHERE state='sending'` CAS no-ops, it MUST unconditionally append the ts to `dispatch_audit` and then attempt `CAS ambiguous → delivered(ts)` first and `CAS manual → delivered(ts)` as fallback — canonical proof always lands durably and wins over inference regardless of which state the resolver reached first (R2 amended).

### 6.3.1 Resolver specification
- **Normalization first**: rows in `sending` with `lease_until_ms < now` are CASed to `ambiguous` (audited `lease_expired`) before any verdict; **all verdict CASes run WHERE state='ambiguous' only** — no verdict races a live consumer CAS.
- **Query**: `conversations.history(channel = destination channel, oldest = (created_ms/1000) − 300, inclusive = true, limit = probed page size, include_all_metadata = true)` [E-A14]; **no `latest` bound** (scan up to Slack-now; the cooling-off floor governs the upper edge); ms→seconds conversion at this boundary only.
- **Pagination exhaustion** := `response_metadata.next_cursor` empty AND `has_more` false; an absent `response_metadata` counts as an empty cursor; the contradictory state (empty cursor AND `has_more` true) is INCONCLUSIVE, never exhaustion; a partial scan is never absence.
- **Match**: `message.metadata.event_type == "github_relay_delivery"` and `metadata.event_payload.delivery_id == GUID` (top-level messages only — R15).
- **Verdicts** (each in one `batch()` with an audit row): **FOUND** → `→ delivered(ts, channel)`; **PROVEN-ABSENT** → `→ manual`, carrying its full evidence in the audit row (scan window, pages, exhaustion proof, floor timestamp, retention check) and raising the observer alarm — it never schedules a resend by itself; the verdict is permitted ONLY when ALL hold: `now ≥ last_send_start_ms + 30 000 (client timeout) + 90 000 (lease) + 60 000 (margin)` — the **cooling-off floor**. The floor guarantees no CLIENT-side attempt is still executing (our fetch aborts at 30 s; the lease has expired; the worker invocation is gone); Slack documents NO maximum latency for a request's effects to materialize [E-A16], so a server-side late post beyond the floor remains possible in principle — that residue is not assumed away but detected and repaired by §6.3.2. Further preconditions: pagination exhausted; workspace retention verified ≥ resolver horizon (R9); metadata round-trip proven in F2 (R14); **INCONCLUSIVE** otherwise (history 429/error/partial scan/floor not reached) → stay `ambiguous`, `resolver_attempts + 1`; after 6 attempts within 1 h → `manual`; audited per attempt.
- **Budget**: ≤ 2 rows per cron run × ≤ 3 pages per row. **F0 probe (house empirical practice)**: with the real bot token, probe the accepted `limit` and sustainable request rate on `conversations.history`, and prove the metadata round-trip (post + re-find via this exact match rule; `metadata_must_be_sent_from_app` must NOT fire for the bot token [E-A15] — if it does, the fallback correlation key is the GUID embedded in a fixed block element, and the match rule switches to it before F2). If the 2025 clampdown applies (1 req/min, 15 objects), the degraded budget makes exhaustion infeasible — a documented DECISION POINT before F2, not a silent degradation.
- **Persistence**: `dispatch_outbox.resolver_attempts`, `dispatch_outbox.last_send_start_ms`; every verdict and every inconclusive attempt appends to `dispatch_audit`.

### 6.3.2 Duplicate repair (closes the undocumented-latency residue)
Whenever the resolver's match rule returns MORE THAN ONE message carrying the same `metadata.event_payload.delivery_id` — the signature of a late server-side materialization after a legitimate resend — the EARLIEST `ts` is canonical: it is recorded on the row (`delivered`), and every later copy is deleted via `chat.delete` (documented; with a bot token the method "may delete only messages posted by that bot" [E-A16] — exactly our case, `chat:write` scope already held). Each deletion is audited (`dispatch_audit` row with both timestamps) and raises an alarm on `/status` (`repaired_duplicates` counter), so a nonzero rate is visible instead of silent. The FOUND verdict therefore subsumes repair: found-one ⇒ record; found-many ⇒ record earliest + delete rest + audit + alarm (RED R17).

### 6.3.3 Mandatory post-resend verification (closes the delivered-and-forgotten gap)
A row delivered via an OPERATOR resend (`manual → queued`, the only resend path) does NOT leave the resolver's attention: it carries `verify_scans_remaining = 2` and `verify_after_ms = delivered_at + 15 min`. Rows with `verify_scans_remaining > 0` and `verify_after_ms ≤ now` are resolver inputs EVEN IN state `delivered`. Each verification scan runs the §6.3.1 match rule over the full window (row `created_ms − 300 s` → now): exactly one match ⇒ decrement `verify_scans_remaining` and schedule the second scan at `delivered_at + 24 h`; more than one match ⇒ **repair from `delivered`** — the EARLIEST ts becomes canonical (`CAS delivered → delivered` updating the recorded ts if needed), every later copy is deleted via `chat.delete`, both actions audited, `repaired_duplicates` incremented (RED R18). A late materialization beyond the 24 h horizon is a documented accepted residual — with the explicit property that it is never unrepairable: ANY later scan that observes a multi-match (including an operator-triggered sweep from the menu) applies the same repair (RED R19). Verification scans share the resolver's budget and are INCONCLUSIVE-safe: a failed scan does not decrement the counter.

### 6.4 Schema (migration 0010, additive only; nothing existing is dropped)
`dispatch_outbox(delivery_id PK, destination CHECK IN('alerts','activity'), shadow INTEGER NOT NULL DEFAULT 0, payload_json CHECK json_valid, state CHECK IN('queued','sending','ambiguous','manual','delivered','dead_letter','closed_manual'), attempt_count, resolver_attempts INTEGER NOT NULL DEFAULT 0, last_send_start_ms, lease_until_ms, next_attempt_ms, verify_after_ms, verify_scans_remaining INTEGER NOT NULL DEFAULT 0, slack_channel_id, slack_message_ts, last_error, created_ms, updated_ms, CHECK(state != 'delivered' OR slack_message_ts IS NOT NULL))` with `UNIQUE(destination, slack_message_ts)`; `dispatch_audit(seq PK AUTOINCREMENT, delivery_id, from_state, to_state, evidence_json, actor, at_ms)`. One time unit everywhere (ms; the stored `slack_message_ts` is an opaque Slack identifier, never arithmetic) — kills D14. No checkpoint, no frontier, no clamps, no hydration — kills D1–D4, D7.

### 6.6 Threat model / least privilege
Inbound-from-Slack surface REMOVED entirely (`/slack/progress`, `/slack/reconciliation*` deleted; relay signing secret and its rotation retired). Ingress HMAC unchanged (2-slot rotation normalized back to `current`, fixing D13). Internal Slack app bot token, minimal scopes: `chat:write` + `channels:history` + `channels:read` (the F3 preflight verifies bot membership in the two REAL channels via the members API), bot invited to the channels (avoids `chat:write.public`); token in Cloudflare Secrets Store; egress allowlist: `slack.com/api/chat.postMessage`, `slack.com/api/conversations.history`, `slack.com/api/conversations.members`, `slack.com/api/chat.delete` (duplicate repair, §6.3.2 — same `chat:write` scope, own messages only [E-A16]). `metadata` carries only the delivery GUID + attempt (non-secret). `/status` exposes aggregate counters only.

### 6.7 Observability, SLOs, bounds
`/healthz` = pure liveness (never fails for operational debt — kills D11). `/status` GET read-only: per-state × per-destination counters + oldest non-terminal age + `repaired_duplicates`. Observe-only scheduled job: alarm ONLY if `dead_letter>0` OR `manual>0` OR an `ambiguous` older than 30 min OR `repaired_duplicates` increased since the last observation. SLOs: p95 webhook→message < 60 s; ambiguous resolved (found or escalated with evidence) < 10 min (subject to the cooling-off floor: rows born from timeouts resolve in ≈3–8 min by design); operator action required ONLY for proven-absence candidates and config errors — expected rare on low-volume alert channels, alarmed within minutes, never silent. Consumer `max_concurrency 1` per queue; resolver budget per §6.3.1; one `*/5` cron (re-enqueue stale `queued` rows + resolver). No log pagination, no catch-up loops.

### 6.8 Migration (nothing deleted; no message duplicated; no message stranded)
**Presence fence (replaces the terminal-state fence):** in every `DISPATCH_MODE`, the ingress accepts a GUID as NEW only if it has NO row in the OTHER path's table (any state — non-terminal rows like `accepted_by_trigger` or `ambiguous` mean "possibly already posted", so they block cross-path acceptance; `shadow=1` rows are EXCLUDED from this check). Same-path handling of an already-present GUID: terminal row ⇒ acknowledge and drop; non-terminal ⇒ route to that row's own recovery (republish the queue intent for a stale `queued` row; otherwise leave it to resolver/menu) — never a fresh row. The fence performs read-only PK lookups on `deliveries` indefinitely; this is compatible with — indeed the purpose of — keeping the legacy tables in D1 forever (they can never be dropped without breaking the fence). The GitHub redelivery workflow passes through the same ingress and the same fence.
**F0 (operator)**: create the internal Slack app; invite the bot to `#github-alerts`, `#github-activity`, `#github-alerts-canary`, `#github-activity-canary`; store the token; verify workspace message-retention policy (R9); run the §6.3.1 empirical probes (history limit/rate; metadata round-trip; `metadata_must_be_sent_from_app`).
**F1**: dispatcher in the SAME worker behind `DISPATCH_MODE off→shadow→primary`; migration 0010; old path untouched; the ADR document lands in the repository under docs/adr/ in this same pull request.
**F2 (natural shadow canary ≥ 72 h)**: the ingress `batch()` atomically inserts the old-path row AND the `shadow=1` outbox row (a 5xx to GitHub implies neither committed); shadow sends target canary channels only (R7). **Parity gate**: (a) mechanics — shadow outbox rows == ingress-accepted GUIDs in the window; (b) delivery — shadow `delivered` count vs old-path rows reaching a delivered state in the window, with old-path ambiguous residue explicitly listed in the runbook (not silently waived); (c) resolver round-trip — 100% of shadow sends re-found via the resolver's own match rule (R14), not merely `ts`-recorded; (d) 0 unresolved `ambiguous`, 0 DLQ.
**F3 (cutover, ordered — every step REVERSIBLE)**: (0) preflight — verify bot membership in both REAL channels via the members API; (1) flip ingress to `primary`; (2) old consumers DRAIN the old-path backlog to zero with all rows terminal — drain verification STARTS only after the new config is confirmed live on all traffic, and the zero-count must be observed twice with an interval exceeding the queue's max-retry latency (non-atomic flag propagation is thereby absorbed into the drain set); any old-path `dead_letter` produced during F2/F3 is imported into the outbox via the operator menu (`manual → queued`) so no GUID is stranded with only a shadow/canary delivery; (3) DISABLE the old queue consumers — and nothing else: the Slack Workflow app, its triggers, the receipt endpoints and the old monitor all SURVIVE F3, so the old path remains fully restorable.
**Rollback regime A (any time before F4)**: (1) flip ingress back to old mode for NEW events AND re-enable the old consumers (both preserved by construction — the app and triggers still exist); (2) the new-path consumers, cron and resolver REMAIN RUNNING until every non-shadow `dispatch_outbox` row is either terminal or parked in `manual` with its evidence and alarm (drain via `/status`; R16) — GitHub already received 2xx for these GUIDs, so no other path will ever deliver them, and `manual` rows are never abandoned by the flip; (3) only then idle the dispatcher. GUIDs delivered by the new path are fenced from old-path re-acceptance by the presence fence (R11) — rollback cannot duplicate and cannot strand.
**F4 (the POINT OF NO RETURN — requires the full §7 E2E gate + a ≥48 h green soak in primary + explicit operator approval)**: retire the Slack Workflow app (operator deletes triggers), remove receipt endpoints, replace the old monitor with the observe-only job, remove dead code (D8/D9) and bridges. All legacy tables REMAIN in D1, frozen read-only (reads by the fence continue). **Recovery regime B (after F4)**: the old path no longer exists by deliberate, gated decision; recovery is ROLL-FORWARD (fix and redeploy the dispatcher) or emergency degradation `DISPATCH_MODE=off` — ingress keeps accepting and persisting every GUID (rows accumulate in `queued` and the observer alarms), egress pauses, and nothing is stranded: on redeploy each accumulated row re-enters the NORMAL pipeline under the SAME I1 contract as ordinary operation — the claim CAS guarantees no row is sent by two concurrent claims and no row is skipped, and each send outcome is classified by §6.2 exactly as usual (this is not an exactly-once promise; exactly-once does not exist anywhere in this design) (R20).

## 10. Hybrid amendment (operator decision 14/08/2026)

Operator decision recorded in issue #192, comments 5299926704 (the gap analysis of the official app) and 5299997975 (the decision itself). This amendment narrows §6 and §9 without reopening the ratified design: less custom surface, official-first wherever the official product already covers the need.

- **H1 — The official "GitHub for Slack" app owns `#github-activity`.** That app subscribes to the activity events natively, so the dispatcher stops carrying them. The three gaps recorded in comment 5299926704 are exactly why `#github-alerts` STAYS on the dispatcher: (a) there is no conclusion/failure filter — the official app's workflow subscription filters are only name, actor, branch and event, so "notify only on failure" cannot be expressed; (b) there is no security-alert subscription of any kind — Dependabot, code scanning and secret scanning alerts are not subscribable; (c) run results appear only as thread replies, and the threading toggle covers only PR/Issue notifications, so a failing run is never a top-level message. Everything the alerts channel exists for falls inside (a)-(c).
- **H2 — The dispatcher is reduced to the single destination `alerts`.** `DispatchDestination` becomes the single literal `"alerts"`; `DISPATCH_CHANNELS` keeps only `#github-alerts` (C0BMUK793NV); the `/status` per-destination counters are keyed by that one destination. A delivery normalized to `activity` (src/domain.ts, unchanged) keeps flowing through the UNTOUCHED legacy path in every `DISPATCH_MODE` — in primary it takes the legacy insert and the legacy, unmarked queue publish; in shadow it gets NO paired shadow row. The dispatcher's ingress, outbox, consumer, resolver and cron therefore only ever see alerts deliveries.
- **H3 — Migrations 0010/0011 are untouched.** They are already applied, and rewriting an applied migration is forbidden. `dispatch_outbox.destination CHECK IN('alerts','activity')` therefore still admits `activity` at the SQL level. That residue is inert: after H2 no code path writes that destination, and the two schema-level REDs that exercise it (the CHECK rejection of an unknown destination and the `UNIQUE(destination, slack_message_ts)` cross-destination case) keep pinning migration 0010's frozen shape.
- **H4 — Phases.** F2, F3 and F4 remain valid as written, scoped to the alerts path. The migration of `#github-activity` to the official app becomes an F3 operational step: subscribe the official app to the activity events, verify the channel receives them, and only then stop the legacy activity path. Neither F2's parity gate nor F4's point-of-no-return changes in substance.
- **H5 — §6.10 R6 narrowed.** "Destination independence" is vacuous with a single destination. The RED is restated as ROW independence inside `alerts`: a transition on one row leaves every other row's state, `updated_ms`, `slack_message_ts` and audit history untouched. ### 10.1 Residual risks

- **Residual 1 (ELIMINATED) — mode-off retries could dead-letter a healthy row.** The consumer previously answered a mode-off message with `retry({ delaySeconds: 60 })`. Every retry consumed the queue's finite retry budget, so a long mode-off window pushed the message to the DLQ; if the operator re-enabled the mode before that DLQ message was consumed, the DLQ handler's mode-off guard no longer applied and a perfectly healthy `queued` row was transitioned to `dead_letter` — recoverable only through the operator menu, which §6.8/R20 forbids ("each accumulated row re-enters the NORMAL pipeline"). Raised by codex in cross-review round 4 and FIXED rather than declared: in mode off the consumer now ACKS the message. The row stays `queued` and untouched (visible through the `queued_backlog_stale` alarm), no retry budget is consumed, no DLQ trip happens, and the cron's stale-queued republish — already gated on `mode !== "off"` — re-enters the row automatically on re-enable, with no operator step.
- **H7 — the relay signing secret is REPURPOSED, not retired.** §6.6 retires the inbound-from-Slack surface together with `SLACK_RELAY_SIGNING_SECRET` and its rotation. The operator menu of §6.2/§6.3 needs an authenticated caller, and adding a binding or a secret would widen the surface for no gain, so the operator route (`POST /dispatch/operator`) signs with that same secret over a version-tagged canonical (`dispatch_operator_action_v1`, which domain-separates it from every legacy canonical). Consequence for F4: the secret and its two-slot rotation SURVIVE as the operator-console credential; only the Slack-facing endpoints and their canonicals are removed. F4's checklist therefore reads "retire the inbound-from-Slack endpoints and canonicals" rather than "retire the relay signing secret". If the operator console is ever moved behind an identity-aware proxy, this credential retires with it.

- **Residual 2 (OPEN) — the `changes() > 0` guard chain is proven only against the test harness.** `insertShadowPaired` (src/dispatch/wiring.ts) relies on `changes()` reflecting the immediately preceding statement of the same `batch()`, so that the shadow row commits only when the legacy insert actually inserted and the audit row only when the shadow row actually inserted. That behavior is currently exercised against the `node:sqlite` harness; it must be re-verified against real D1 during F2 before the parity gate is read as green.
